# Meta WhatsApp test-number setup

Checked **10 November 2026**. This repository implements an official Cloud API adapter and offline transport tests. No Meta account, callback, approved recipient, template, or live message was created during development. Passing local tests is not evidence of delivery or use-case approval.

## Eligibility is still unresolved

Before connecting an account, assess whether the exact interviewing product is permitted under the current terms accepted by that account. AI interviewing may be the primary product; a focused research study does not establish eligibility. Record the product purpose, account owner, intended countries, processors, consent, human-support route, and data handling, then obtain the required account/platform assessment before real participant research. The [deployment gates](DEPLOYMENT.md#before-participant-research) provide the repository's self-contained launch checklist. The current [Meta Terms for WhatsApp Business Platform](https://www.facebook.com/legal/Meta-Terms-for-WhatsApp-Business-Platform) could not be read during this check: the [former terms URL](https://www.whatsapp.com/legal/business-solution-terms) redirected to a Facebook login/block page. Older indexed country exceptions are not current clearance for EEA, Brazil, or any other deployment. Obtain the accepted terms and a written Meta/authorized-provider assessment of this exact product, account owner, countries, and processors before real participant research.

The current [Business Messaging Policy](https://whatsappbusiness.com/policy/) was readable and dated 23 September 2026. It requires opt-in, honoring opt-outs, approved templates to initiate conversations, and a 24-hour user-message window for free-form replies. Automation also needs a usable human escalation path and appropriate data notices. Account provisioning, technical access, and template approval do not resolve AI-provider eligibility. A controlled technical test with synthetic content is distinct from launching research.

## Provision the test surface

The following are operator steps to complete in Meta's authenticated console. Exact labels and availability may vary; the current [get-started reference](https://developers.facebook.com/documentation/business-messaging/whatsapp/get-started) returned a login page during review.

1. Use a Meta developer account authorized for the business. Create/select a developer app with WhatsApp Business Platform access and select its WhatsApp API setup screen. Use Meta's test number initially, rather than migrating a real business number.
2. Record the **Phone Number ID** for the test sender and the **WhatsApp Business Account ID** separately. The gateway takes the Phone Number ID, not the displayed phone number or business account ID.
3. Add a tester-controlled recipient through the console's permitted-recipient flow and complete the verification code process. Use only explicitly consenting testers. Recipient verification does not replace research consent or messaging opt-in. Confirm the current test-number recipient limit in the console rather than assuming a historical limit.
4. Obtain a temporary test access token from the console. Copy the app secret from app settings into local secret configuration. Keep both outside source control, screenshots, logs, and browser dashboard code. A token with `whatsapp_business_messaging` is needed for messaging; grant management permissions such as `whatsapp_business_management` only for authorized account-management operations. Check current permissions and asset assignment in Meta before use. Temporary tokens expire; follow the current system-user token process and least-privilege asset assignment for any later deployment.
5. Select an explicitly supported Graph API version in the console and verify its sunset date against the [version lifecycle](https://developers.facebook.com/docs/graph-api/changelog/versions). This reference returned HTTP 429 during review, so **no current supported version is asserted here**. The gateway rejects missing/malformed versions and deliberately supplies no default. `v99.0` in automated tests is a fake transport fixture, never a deployment value.
6. Choose a separate unpredictable webhook verification token. This token is for the callback handshake; it is **not** the app secret and does not authenticate webhook POST bodies.

## Connect the callback

Expose **`/webhooks/whatsapp`** on the backend through a publicly reachable HTTPS URL with a valid certificate. Both verification GET and event POST use that path. Keep operator/dashboard endpoints behind their own authentication. Do not expose a development server holding real participant data.

In the app's WhatsApp webhook configuration, enter that callback URL and the same verification token configured on the backend. Meta's verification GET supplies `hub.mode`, `hub.verify_token`, and `hub.challenge`; the backend checks mode/token and returns the challenge. Configure the WhatsApp Business Account's `messages` subscription and ensure the app is subscribed to the intended account. The same subscription carries inbound messages and outbound delivery-status updates. Merely verifying the callback URL does not establish account subscription.

For POSTs, verify `X-Hub-Signature-256` using HMAC-SHA256 with the app secret and the **original raw request body**, before JSON parsing or queueing work. The [Graph webhook reference](https://developers.facebook.com/docs/graph-api/webhooks/getting-started) returned HTTP 429 during review; confirm the console instructions against the authenticated reference. The adapter's parser filters `metadata.phone_number_id` to the configured sender and retains unsupported-message error records. Parsing is deliberately stateless: persist incoming message IDs and acknowledge duplicate deliveries without producing another research turn or outbound message. Persist the accepted event before acknowledging; process slow audio/model work outside the webhook request.

## Gateway configuration and behavior

`MetaGateway(access_token, phone_number_id, graph_api_version, client=None)` accepts server-side secrets and an explicit version. Call `aclose()` during shutdown for a gateway-owned HTTP client. Tests inject `httpx.MockTransport`, with no live credentials.

| Input | Purpose |
| --- | --- |
| `WHATSAPP_ACCESS_TOKEN` | Bearer authorization to Graph and approved media host |
| `WHATSAPP_PHONE_NUMBER_ID` | Scope incoming events and outbound messages to one sender |
| `WHATSAPP_API_VERSION` | Explicit `vNN.N` value verified by the operator |
| `WHATSAPP_APP_SECRET` | Validate signed POST body via `verify_signature` |
| `WHATSAPP_VERIFY_TOKEN` | Backend GET handshake, separate from signature verification |
| `WHATSAPP_DISPLAY_NUMBER` | Test sender's digits-only international number, used for participant links |
| `WHATSAPP_BUSINESS_ACCOUNT_ID` | Account identity for operator setup; distinct from Phone Number ID |
| `WHATSAPP_TEST_MODE=true` | Keep the deployment restricted to controlled testing |
| `TEST_RECIPIENT_ALLOWLIST` | Comma-separated verified tester numbers, digits only |
| `APPROVED_TEMPLATES` | Comma-separated names populated only after verifying approval and intended locale |

The backend reads these uppercase environment names directly, with **no `ECHO_` prefix**, from its process environment or the settings file selected by `ECHO_ENV_FILE` (default `.env` in the backend working directory). The dashboard's server connection settings are separate. Backend startup also requires a valid Fernet `ENCRYPTION_KEY`; local access requires `MODE=local`, `AUTH_MODE=local`, and a random `RESEARCHER_TOKEN` of at least 32 characters. Keep the encryption key stable and secret: rotating it without a migration makes existing encrypted records unreadable and changes phone HMACs. Configure `DATABASE_URL`, `OPENAI_API_KEY` (or approved `OPENAI_KEY_FILE`), `TRANSCRIPTION_MODEL`, `DECISION_MODEL`, `RETENTION_DAYS`, `SUPPORT_CONTACT`, and `PRIVACY_NOTICE_URL` before the corresponding processing is used. Production requires PostgreSQL and the configured researcher authentication. `COMMERCIAL_ELIGIBILITY_VERIFIED` must stay false until there is actual recorded clearance; a configuration flag is not approval evidence.

`send_text` accepts the participant's latest inbound timestamp, requires timezone-aware values, and allows an age from zero up to **strictly less than 24 hours**. Future timestamps fail closed. Business replies do not reset this window. The caller must check participant consent/withdrawal immediately before sending and must pass a timestamp belonging to that recipient. This adapter is not a scheduler or consent database.

`send_template` requires explicit messaging opt-in and membership in the configured approved-name set. It supports text parameters in the body only. Configure an actually approved name and matching approved language; name allowlisting cannot prove current upstream approval. Templates may be paused or rejected later. Research invitations/reminders must receive the category determined through Meta's approval process; do not assume they are utility messages. There is no automatic template fallback after free-form expiry.

An accepted API response returns a Meta message ID; it does not establish delivery. Record signed status events, including `failed` and its numeric error code. `GatewayError` exposes only a sanitized code plus `retryable` and `ambiguous`, without including upstream bodies or tokens. A timeout, lost response, malformed success, or server failure may leave an outbound send ambiguous. **Never automatically retry an ambiguous send**, even when a server error is also marked retryable. Persist the send attempt and reconcile delivery/status evidence or require operator review. The adapter makes one request and has no outbound retry loop or assumed Meta idempotency key.

Verified delivery callbacks are durably deduplicated before acknowledgment, including callbacks whose provider ID is not yet attached to an outbound record. The worker reconciles them after saving each send response and on later cycles. Delivery/read proof never regresses to a failure because a callback arrives late. These retained status records contain only the provider message ID, normalized status, timestamp, optional numeric error code, deterministic event hash, and expiry; they contain no raw webhook body or phone number and expire through the retention job.

## Run and recover the worker

For a fresh local SQLite setup, initialize from `backend` with `../.venv/bin/python -m echo.manage init-db`, then run `../.venv/bin/python -m echo.worker` beside the API process. For PostgreSQL/Supabase, apply administrator migrations first; do not initialize the schema using the restricted runtime role. The worker deliberately does not create tables. Follow the [quickstart](../README.md#local-quickstart) or [database setup](../supabase/README.md) for the appropriate path. Both processes must use the same database and encryption/configuration. The worker can start without WhatsApp configuration: it reports a waiting state, performs retention maintenance, and makes no Meta or AI calls until a gateway can be configured. Missing OpenAI credentials do not globally disable consent or control commands; an attempted model operation fails safely through the service adapter.

Run only one sender for a database. The CLI holds an exclusive local file lock next to a SQLite database, or a PostgreSQL session advisory lock on a dedicated connection. It checks PostgreSQL connection identity and lock ownership before dispatch and stops if ownership is lost. Use a **direct/session-persistent PostgreSQL connection**, never a transaction-pooling endpoint for this worker: the lock must remain attached to one database session. The locking behavior follows PostgreSQL's [session advisory-lock semantics](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS) and [lock-view representation](https://www.postgresql.org/docs/current/view-pg-locks.html). Local file-lock behavior and an actual PostgreSQL session lock, release/reacquisition, and rejection of a second worker have been verified. Docker services remain unexecuted.

On startup under the lock, interrupted inbox `processing` returns to `queued`; model/media reads may safely repeat, with possible duplicate model cost. Outbox `sending` becomes `uncertain`, never `pending`. Each attempt commits `sending` before the network call, then records the Meta ID on acceptance. Definitive errors become `failed`; uncertain outcomes remain `uncertain`. Neither is automatically retried. Before every send the worker rechecks opt-out, configured tester permission, retention expiry, and the latest genuine inbound timestamp. One control acknowledgment may send after opt-out; ordinary research messages are suppressed. A STOP received after an HTTP request has already been dispatched cannot recall that request; it blocks subsequent messages.

Inbox and outbox ordering use high-resolution application receipt/creation timestamps, with the message ID only as a final tie breaker. This preserves locally received order when several records share the same second; it does not reconstruct the sender's chronology if Meta delivers events out of order. Multiple API servers need synchronized clocks; a database sequence or stronger per-participant ordering should replace application timestamps before a distributed rollout.

The worker scrubs expired inbox/outbox payloads and interview turns, clears expired interview pathway/state/consent ciphertext, and preserves the study/project definitions. When no retained interview or unexpired message needs a participant's contact details, it clears the encrypted phone. Only an opted-out participant retains the phone HMAC as a suppression tombstone; other orphan identity hashes are randomized. Fresh unprocessed invitation messages retain their contact until their own expiry. Backups, provider retention, external exports, and records outside this database need their separately documented deletion process.

## Audio path and security boundaries

For an audio message, the gateway retrieves Graph metadata using the media ID and configured Phone Number ID, then downloads the returned URL using bearer authorization. It allows HTTPS only on `lookaside.fbsbx.com` or a subdomain of that exact domain, with no credentials, custom port, fragment, or redirects. This is a deliberately narrow local allowlist. A different legitimate Meta host must be reviewed before expanding it; never accept an arbitrary webhook-provided URL or follow a redirect with the token.

Both declared metadata size and actual streamed bytes are limited to **16 MiB**, a local safety limit. The gateway requires a supported metadata MIME and matching download `Content-Type`: AAC, MP4, MPEG, AMR, or OGG audio. It returns normalized MIME without codec parameters. Headers are not proof of file integrity: the downstream audio/transcription boundary must inspect/decode the file, enforce duration/codec constraints, and reject corrupt content before processing. Media IDs, download URLs, access tokens, raw participant audio, and transcripts should not appear in ordinary logs. Do not persist the temporary URL; retrieve a new one through metadata if necessary.

The current [media reference](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-phone-numbers/media) and [inbound audio webhook reference](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/messages/audio) returned HTTP 429 on this check. Consequently the local cap, MIME list, and host are implementation safeguards awaiting authenticated real-device confirmation, not claims of freshly verified platform format/size support. Test voice notes and audio attachments separately. Keep a text retry path for unsupported or unavailable audio.

## Controlled test checklist

Complete these with tester-owned numbers and synthetic content after provisioning. Recorded gateway tests cover offline provider boundaries; they are not evidence that this checklist passed on a real account.

- Verify the callback handshake, then verify that an altered/missing-signature POST is rejected and an event for another Phone Number ID is ignored.
- Send an inbound text from the approved tester. Confirm a single stored message and reply. Replay its signed webhook and confirm no second turn/send. Confirm a delivery or read event and exercise a failed delivery event.
- Send a short voice note and an audio attachment from actual devices. Confirm authenticated metadata/download, decoding/transcription, consent checks, and a text reply. Test expired media, unsupported/corrupt audio, and size/duration limits without storing unnecessary raw audio.
- Exercise the exact 24-hour boundary and a delayed queued reply. Confirm expiry does not trigger a free-form send. Separately test only an approved template to an opted-in approved tester.
- Stop/withdraw, then confirm queued replies and reminders cannot send. Test the human-support route. Inject an outbound timeout and verify the attempt becomes ambiguous without automatic resend.
- Retain test evidence with redacted identifiers, chosen API version/sunset date, current approved template/locale, device/audio results, and subscription status. Keep live research disabled until policy, privacy, and operational gates in the [deployment checklist](DEPLOYMENT.md#before-participant-research) are satisfied.

Run offline gateway tests from `backend` with `../.venv/bin/python -m pytest tests/test_gateway.py -q -o asyncio_default_fixture_loop_scope=function`. The suite covers signature integrity, selected-number parsing, unsupported errors, replay determinism, failed statuses, media URL/token containment, redirects, metadata and streamed limits, window boundaries, template gates, and ambiguous outbound failures. It does not prove account setup or live delivery.
